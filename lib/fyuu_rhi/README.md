# FyuuRHI

[API Reference](https://platiscsan.github.io/fyuu-engine/en/html/) · [简体中文](README.zh-CN.md)

FyuuRHI is FyuuEngine's low-level rendering interface. It provides one C++23
API for device discovery, resource and pipeline creation, command-graph
execution, synchronization, and presentation while keeping native graphics
objects behind backend-neutral handles.

The API is still evolving. A backend being available in a build does not imply
that every platform path has been validated.

## Backends

| Backend | Intended platforms | Current validation |
| --- | --- | --- |
| Direct3D 12 | Windows | Built and exercised on Windows |
| Vulkan | Windows, Linux | Exercised on Windows; Linux needs runtime validation |
| OpenGL | Windows, Linux | WGL, GLX, and EGL paths; exercised on Windows |
| WebGPU | Windows, Linux, Apple platforms | Dawn-based; exercised on Windows |
| Metal | macOS, iOS | Implemented but **not yet validated** on Apple hardware |

Treat Metal as experimental until it passes Apple toolchain, presentation,
resize, diagnostics, and shutdown tests on real devices.

## Requirements and integration

FyuuRHI requires CMake 3.28 or newer, C++23, and a compiler with named-module
support. Link the library and import its public module:

```cmake
target_link_libraries(MyApplication PRIVATE FyuuRHI)
set_target_properties(MyApplication PROPERTIES CXX_EXTENSIONS OFF)
```

```cpp
import fyuu_rhi;
```

```cpp
for (auto backend : fyuu_rhi::EnumerateBackends()) {
```

## Object model

The public API follows the lifetime of a rendering device:

1. `Instance` enumerates the physical devices exposed by one backend.
2. `PhysicalDevice` describes an adapter and creates a `LogicalDevice`.
3. `LogicalDevice` creates resources, samplers, pipelines, and schedulers.
4. `Resource` creates buffer or texture views of itself.
5. `Pipeline` creates resource groups matching its reflected shader interface.
6. `CommandScheduler` builds and executes command graphs.

Physical devices, logical devices, resources, views, samplers, pipelines, resource
groups, and completion tokens use fast pimpl with inline storage. Their opaque
implementations need no separate allocation. Size and alignment are checked at
compile time, and moved-from objects are empty.

Native objects remain opaque. Objects from different backends or different
logical devices must never be mixed. Most GPU objects are move-only owners;
`CommandScheduler` is copyable and shares its scheduling context. Starting a
graph moves all bound objects into the operation, and the receiver gets them
back when the operation succeeds, fails, or is stopped.

## Initialization and device selection

Initialize the process-wide context before requesting a backend. The log sink
is called synchronously and must remain alive until `RebindRHISink()` replaces it.
`InitializeRHIContext()` may be called repeatedly: each call updates names, versions,
cache configuration and platform state, and synchronously replaces the Sink (or
disables logging when passed `nullptr`). Serialize initialization with other RHI
operations; previously borrowed metadata string views may be invalidated. Existing
Vulkan-derived objects must be released before reinitialization. The Vulkan Instance
is retired and recreated on its next request; other backend roots are retained.
No Runtime lifetime reference is acquired.
Each initialization also retires the Slang global session after active compilation
finishes. Each compile miss uses a local session so loaded module names cannot
retain stale source. Valid disk-cache hits remain session-free, and existing
pipeline outputs stay valid.

```cpp
fyuu_rhi::InitializeRHIContext(
    "MyApplication",
    { 0u, 1u, 0u, 0u },
    "MyEngine",
    { 0u, 1u, 0u, 0u },
    &log_sink
);
```

`RequestInstance` returns the process-lifetime instance for the selected backend:

```cpp
auto& instance = fyuu_rhi::RequestInstance(fyuu_rhi::Backend::Vulkan);
auto physical_devices = instance.EnumeratePhysicalDevices();
auto const& physical_device = fyuu_rhi::BestPerformance(physical_devices);
auto device = physical_device.CreateLogicalDevice();
auto scheduler = device.CreateScheduler();

// Create resources and submit command graphs here.
```

`PhysicalDevice::GetInfo()` returns the adapter name and type plus optional
vendor, device, and dedicated-memory information. A missing optional value
means that the backend cannot report it; it does not mean zero.

`Instance::ShareContextOnThisThread()` binds the shared OpenGL context where
OpenGL requires it. Other backends treat the call as a no-op.

## Resources and views

`ResourceFlags` describes memory placement, usage, format, texture shape,
sample count, and allowed view kinds. These flags are a correctness contract:
backends reject contradictory combinations, and every recorded use must have
been declared when the resource was created.

```cpp
fyuu_rhi::ResourceFlags flags;
flags.Set(fyuu_rhi::ResourceFlagBits::DeviceLocal);
flags.Set(fyuu_rhi::ResourceFlagBits::Texture2D);
flags.Set(fyuu_rhi::ResourceFlagBits::TextureView2D);
flags.Set(fyuu_rhi::ResourceFlagBits::TextureViewAspectAll);
flags.Set(fyuu_rhi::ResourceFlagBits::RenderAttachment);
flags.Set(fyuu_rhi::ResourceFlagBits::CopySRC);
flags.Set(fyuu_rhi::ResourceFlagBits::Sample1);
flags.Set(fyuu_rhi::ResourceFlagBits::R8G8B8A8Unorm);

auto texture = device.CreateTexture(width, height, 1u, 1u, flags);
auto view = texture.CreateTextureView(0u, 1u, 0u, 1u, flags);
```

Attachment textures may pass a final `TextureClearValue` to `CreateTexture`:
`ColorClearValue{r, g, b, a}` for color, or `DepthStencilClearValue{depth, stencil}`
for depth/stencil. This is metadata, not texture initialization. Use
`LoadOperation::ClearDefault` on an attachment to clear with that texture's default;
`LoadOperation::Clear` continues to use the explicit attachment value. Depth and
stencil select their load operations independently.

Omitting the value gives attachment textures transparent black or depth 1/stencil 0.
Non-attachment textures cannot specify a clear value. All backends use these
defaults during rendering; D3D12 additionally supplies them as optimized clear
values at resource creation. An explicit override remains valid, but a different
value may trigger a D3D12 fast-clear performance warning.

Views are created by their source resource so backend and device ownership can
be checked without exposing native handles. Use `CreateBufferView()` for
buffers. A buffer written by `WriteBuffer`, for example, must include
`CopyDST`; `VertexBuffer` alone does not permit an upload.

### Mapping buffers

`Resource::Map()` maps a byte interval and returns a move-only
`ResourceMapScope`. All backends require offsets aligned to
`Resource::MapOffsetAlignment` (8 bytes) and non-empty resolved lengths aligned to
`Resource::MapSizeAlignment` (4 bytes). A zero length selects the remaining bytes,
which must still meet these requirements. Invalid intervals throw
`std::invalid_argument` before native mapping.

Buffer/texture copies require offsets aligned to `TextureDataLayout::OffsetAlignment`
(512 bytes), non-zero row pitches aligned to `TextureDataLayout::RowPitchAlignment`
(256 bytes), and non-zero `rows_per_image`. Format block and copy bounds still apply.
The graph rejects misaligned layouts during connection. These constants define a
portable contract shared by every backend, rather than backend minimum limits.

A `HostVisible` buffer is writable; pass bytes to
`ResourceMapScope::Write()` instead of retaining a backend mapping pointer.
A `DeviceReadback` buffer is readable through `ResourceMapScope::Read()`.

On WebGPU, `HostVisible` buffers allow only an additional `CopySRC` usage, and `DeviceReadback` buffers allow only an additional `CopyDST` usage. Neither policy can be combined with vertex, index, uniform, storage, texel or indirect usages. Unsupported combinations throw `std::invalid_argument` at creation instead of silently dropping mapping support. Upload GPU vertex data through a separate staging buffer.
Keep the Resource alive and do not move it until the mapping ends.

```cpp
fyuu_rhi::ResourceFlags upload_flags;
upload_flags.Set(fyuu_rhi::ResourceFlagBits::HostVisible);
upload_flags.Set(fyuu_rhi::ResourceFlagBits::CopySRC);
auto upload = device.CreateBuffer(data.size(), upload_flags);

{
    auto mapping = upload.Map({ 0u, data.size() });
    mapping.Write(std::as_bytes(std::span(data)));
} // Automatically unmaps here.
```

GPU work that reads or writes the interval must not overlap the mapping. Wait
for the command graph completion before mapping a readback buffer. Textures
cannot be mapped directly: copy the required texture region into a
`DeviceReadback` buffer first, then read the buffer.

```cpp
auto mapping = readback.Map({ 0u, byte_count });
auto bytes = mapping.Read();
Consume(bytes);
mapping.Reset(); // Optional early unmap; destruction is otherwise sufficient.
```

`Write()` rejects readback mappings and data larger than the mapped interval.
`Reset()` is idempotent, and a moved-from or already reset scope owns no active
mapping. The `Resource` must outlive its active mapping scope.

## Shaders, pipelines, and resource groups

For packed `float3` vertex input, set `VertexAttribute::format` to
`ResourceFlagBits::R32G32B32Float`. It consumes 12 bytes; specify the actual buffer
stride and attribute offset in the vertex layout. This is a vertex-only format,
not a promise of texture or typed-buffer-view support.

Pipelines receive Slang program descriptors. FyuuRHI compiles the declared
modules and reflects their resource interface. A graphics pipeline also
describes vertex input, primitive topology, rasterization, multisampling,
depth/stencil state, blending, and attachment formats.

```cpp
auto pipeline = device.CreateGraphicsPipeline(
    {
        .program = {
            .modules = shader_modules,
            .entry_points = entry_points
        },
        .vertex = {
            .buffers = vertex_buffers,
            .attributes = vertex_attributes
        },
        .color_targets = color_targets
    }
);
```

A resource group is created by its pipeline. Its space, slot, array element,
and binding kind must match the reflected interface. FyuuRHI supports both
separate texture/sampler bindings and an explicitly combined binding:

```cpp
std::array bindings{
    fyuu_rhi::pipeline::ResourceBinding{
        .slot = 0u,
        .array_element = 0u,
        .value = fyuu_rhi::pipeline::BindingValue::FromCombined(
            texture_view,
            sampler
        )
    }
};

auto group = pipeline.CreatePipelineResourceGroup(0u, bindings);
```

## Command graphs

A command graph describes binding slots, dependency-ordered nodes, logical
queue requirements, resource accesses, and commands:

```cpp
using namespace fyuu_rhi::execution;

auto builder = scheduler.schedule();
auto target_resource = builder.RegisterResource();
auto target_view = builder.RegisterView();
auto graphics_pipeline = builder.RegisterPipeline();

auto render = builder.CreateNode(QueueType::Graphics);
render
    .Access(
        {
            target_resource,
            AccessMode::Write,
            ResourceUsage::ColorAttachment,
            {}
        }
    )
    .Record(BindPipeline{ graphics_pipeline })
    .Record(
        BeginRendering{
            .area = { 0, 0, width, height },
            .colors = {
                {
                    .resource = target_resource,
                    .view = target_view,
                    .clear = { 0.02f, 0.03f, 0.04f, 1.0f }
                }
            }
        }
    )
    .Record(Viewport{ 0.0f, 0.0f, float(width), float(height) })
    .Record(Scissor{ 0, 0, width, height })
    .Record(Draw{ 3u, 1u, 0u, 0u })
    .Record(EndRendering{});
```

Access declarations are not hints. They must describe the commands accurately;
the backends use them to form batches, transition resources, insert barriers,
synchronize queues, and transfer queue-family ownership. `QueueType` states a
capability requirement, not a promise of a dedicated physical queue.

## Presentation

Presentation is part of the graph and normally depends on the render node:

```cpp
auto present = builder.CreateNode(QueueType::Present, render);
present
    .Access(
        {
            target_resource,
            AccessMode::Read,
            ResourceUsage::PresentationSource,
            {}
        }
    )
    .Record(
        Present{
            .source = target_resource,
            .target = 0u,
            .buffer_count = 3u,
            .vertical_sync = true
        }
    );
```

Bind each native window with `SetPresentationTarget()`. The application still
owns the window and event loop, responds to size changes, and submits frames
until the window closes.

Before closing a window or switching backends, await all graphs on the logical
device and destroy the old schedulers and backend resources.

Native WebGPU uses FIFO with `vertical_sync=true`. With `false`, it selects
Immediate, then Mailbox, according to surface capabilities, falling back to FIFO
when neither is supported. Changing this setting reconfigures the existing surface.
Browser Canvas presentation is controlled by the browser; this parameter cannot
disable vertical synchronization there.

WebGPU selects a supported surface format. RGBA8/BGRA8 sRGB sources are copied
to the matching UNORM surface format when available, preserving encoded pixels
without another sRGB conversion. When only the other channel layout is supported,
RHI converts RGBA/BGRA through an internal UNORM intermediate texture and a
presentation draw; the source texture does not need sampling usage.

Release does not reset native window state. A Windows window's pixel format is
immutable once assigned, and OpenGL reports incompatible formats explicitly.
Reusing the same HWND across backends is not guaranteed. For arbitrary backend
switching, the host must supply a new native presentation window.

## Starting work and receiving completion

Connect a finished graph to a receiver, fill every registered slot, and start
the operation:

```cpp
auto operation = std::move(builder).connect(Receiver{ state });
operation.BindResource(target_resource, std::move(texture));
operation.BindView(target_view, std::move(view));
operation.BindPipeline(graphics_pipeline, std::move(pipeline));
operation.SetPresentationTarget(native_window);
operation.start();
```

The receiver provides `get_env()` and handles exactly one terminal signal:

- `set_value(CommandGraphResources&&) &&` for success;
- `set_error(std::exception_ptr) &&` for failure;
- `set_stopped() &&` for cancellation.

Before an error or stopped signal, `RecoverBindings(CommandGraphResources&&)`
returns the objects owned by the operation. On success they arrive directly in
`set_value`. Use the matching `TakeResource`, `TakeView`, `TakeSampler`,
`TakePipeline`, or `TakeResourceGroup` operation; each slot can be taken once.

Completion may be delivered from an internal worker thread. The receiver must
synchronize application state shared with that thread. Stop requests are
effective before native submission; already submitted GPU work is not generally
cancellable.

Readback and rendering both use asynchronous `start()` submission. Receivers may submit further graphs, but must not block waiting for another receiver on the completion thread. Express GPU dependencies in the graph and read back buffers after graph completion.

## Validation and diagnostics

Execution proceeds through preparation, parallel command recording, and queue
submission. Binding errors are reported before submission; recording and GPU
errors flow through the receiver's error channel.

Backend diagnostics are written to the configured `fyuu_rhi::log::Sink`.
Use `fyuu_rhi::RebindRHISink(new_sink)` to replace the diagnostic destination.
Pass `nullptr` before destroying the current Sink if no replacement is needed.
Rebinding blocks new admission, waits for all admitted old `Write()` calls to
return, then publishes the new borrowed pointer. A null destination discards
diagnostics without stopping GPU work. Calling before initialization completes
throws `std::logic_error`. Never rebind from `Write()` or while holding a lock
that `Write()` needs. Coordinate Sink lifetimes across concurrent rebinders.
Automated tests should treat Error and Fatal records as failures even when a
backend or process returns success.

Cross-backend regression tests live under `lib/fyuu_rhi/test`. Enable BUILD_TESTING to register them with CTest. Run `DrawProbe <backend> hello` to check triangle pixels. DrawShapes, BindingProbe, GraphValidation and CompletionPool provide rendering-state, binding, graph and concurrency coverage. Window presentation and resize are exercised by native-window host integration checks. Metal still requires validation on Apple hardware.
## Shader cache cleanup

Shader programs are stored under the platform cache directory, followed by
`<engine>/v<version>/<application>/v<version>/shaders/`:

```text
shaders/
  d3d12/                         # also vulkan, opengl, webgpu, metal
    shader-my_material/          # portable, shortened module name
      <variant-hash>/            # source, compiler, driver and options
        manifest.json            # full module/entry names and compilation tag
        interface.json
        reflection.json
        entry-0-shader-vertex_main.bin
        entry-1-shader-fragment_main.bin
```

Windows uses `%LOCALAPPDATA%`; Linux uses `$XDG_CACHE_HOME` or `~/.cache`;
macOS uses `~/Library/Caches`. Close applications using RHI before cleanup.
Delete a variant directory, a shader directory, or a backend directory to clear
that scope; missing entries are rebuilt on the next pipeline creation. Programs
with several modules are grouped under the first module; `manifest.json` lists
all modules. Sanitized names are only labels: hashes still distinguish variants.

Automatic eviction removes whole variants rather than individual files.

Native pipeline caches use the adjacent `pipelines/` directory:

```text
pipelines/
  d3d12/
    graphics/shader-my_material/<hash>.bin
    compute/shader-my_compute/<hash>.bin
    root-signatures/<hash>.bin
  opengl/
    graphics/shader-my_material/<hash>.bin
    compute/shader-my_compute/<hash>.bin
  vulkan/device-shared/<hash>.bin
```

D3D12 root signatures are shared by layout. Vulkan caches are shared by device
and driver, not one shader; clearing `device-shared/` clears that native cache.
WebGPU and Metal currently have no RHI-managed native pipeline disk cache.
Driver/runtime-owned caches are outside this directory. Close RHI applications
before deleting files or directories. Cache misses rebuild the native objects.

## WebGPU progress and CPU usage

Batch recording remains parallel. While queue work is outstanding, the scheduler
drives Dawn with zero-timeout polling and yields between rounds instead of sleeping
on a millisecond timer. This reduces completion latency but uses more CPU while
waiting for GPU work. With no outstanding work, the progress thread sleeps until
a new submission or shutdown notification. Receivers and resource retirement remain
on the completion driver, not on Dawn callbacks or the progress thread.

## WebGPU BC texture fallback

For non-block-aligned dimensions, WebGPU stores BC textures as original BC blocks
plus a decoded sampling texture. Aligned textures retain native BC sampling when
the device supports it; otherwise they also use software decoding.
This preserves the requested dimensions and mip chain, including images such as
2287 × 2279. Buffer copies and readback use the original blocks without recompression;
texture copies update both representations. Decoding is GPU work recorded before
sampling, not a synchronous CPU upload. The temporary native BC image may have padded
dimensions, but the texture seen by application shaders does not.

When `TextureCompressionBC` is unavailable, BC1–BC7 GPU software decoding is
automatic for NVIDIA, Intel and AMD profiles, without an opt-in switch. BC6H/BC7
also have vendor-independent, specification-defined decoders. AMD BC1–BC5 still
await native hardware verification; unknown BC1–BC5 profiles are rejected rather
than approximated.

sRGB remains sRGB. BC4/BC5 use signed or unsigned normalized16 sampling storage
on NVIDIA/Intel, while BC6H uses RGBA16Float. BC1–BC3 and BC7 use RGBA8 storage.
Both representations and temporary decode images consume additional memory.
All WebGPU BC textures keep
original blocks so copy/readback behavior does not depend on image size or compatibility
mode. It does not make BC render targets or writable storage images legal.

## Memory retention

Idle D3D12 command lists, Vulkan command pools and binary completion objects are
retained according to recent graph demand and available host memory, rather than
the largest graph ever submitted. Memory headroom is sampled at most once per
100 ms. Below 25% available memory the idle budget decreases proportionally;
below 5% it becomes zero. Trimming happens during subsequent scheduler activity
or retirement, never by releasing in-flight objects. This policy measures host
memory, not a GPU memory budget.

Vulkan resource groups share descriptor-pool pages. Page capacity grows with
demand and is reduced for new pages under memory pressure; existing live pages
cannot be resized. Empty pages are released when their final group is destroyed.
D3D12 descriptor heaps are created only when first used.

OpenGL keeps owned submission snapshots in contiguous metadata arrays and trims
idle VAO and presentation-target caches. Slang retains only its lazy global session;
compilation sessions retire with each compile operation. WebGPU shares BC
decode pipelines between live textures of the same device and decoded format;
fallback constants use aligned recording-local pages with a separate slice for
each update. None of these changes alter resource ownership or binding semantics.
