# FyuuRHI

[API Reference](https://platiscsan.github.io/fyuu-engine/en/html/) · [简体中文](README.zh-CN.md)

FyuuRHI is FyuuEngine's low-level rendering interface. It provides one C++23
API for device discovery, resource and pipeline creation, command-graph
execution, synchronization, and presentation while keeping native graphics
objects behind backend-neutral handles.

The API is still evolving. A backend being available in a build does not imply
that every platform path has been validated.

## Backends

| Backend | Intended platforms | Current validation |
| --- | --- | --- |
| Direct3D 12 | Windows | Built and exercised on Windows |
| Vulkan | Windows, Linux | Exercised on Windows; Linux needs runtime validation |
| OpenGL | Windows, Linux | WGL, GLX, and EGL paths; exercised on Windows |
| WebGPU | Windows, Linux, Apple platforms | Dawn-based; exercised on Windows |
| Metal | macOS, iOS | Implemented but **not yet validated** on Apple hardware |

Treat Metal as experimental until it passes Apple toolchain, presentation,
resize, diagnostics, and shutdown tests on real devices.

## Requirements and integration

FyuuRHI requires CMake 3.28 or newer, C++23, and a compiler with named-module
support. Link the library and import its public module:

```cmake
target_link_libraries(MyApplication PRIVATE FyuuRHI)
set_target_properties(MyApplication PROPERTIES CXX_EXTENSIONS OFF)
```

```cpp
import fyuu_rhi;
```

## API reference

Open the published [English API reference](https://platiscsan.github.io/fyuu-engine/en/html/),

`FyuuRHIDocumentationZhCN`.

Backend availability depends on the target platform and the dependencies found
at configure time. Query it instead of assuming:

```cpp
for (auto backend : fyuu_rhi::EnumerateBackends()) {
    // Apply the application's backend-selection policy.
}
```

## Object model

The public API follows the lifetime of a rendering device:

1. `Instance` enumerates the physical devices exposed by one backend.
2. `PhysicalDevice` describes an adapter and creates a `LogicalDevice`.
3. `LogicalDevice` creates resources, samplers, pipelines, and schedulers.
4. `Resource` creates buffer or texture views of itself.
5. `Pipeline` creates resource groups matching its reflected shader interface.
6. `CommandScheduler` builds and executes command graphs.

Native objects remain opaque. Objects from different backends or different
logical devices must never be mixed. Most GPU objects are move-only owners;
`CommandScheduler` is copyable and shares its scheduling context. Starting a
graph moves all bound objects into the operation, and the receiver gets them
back when the operation succeeds, fails, or is stopped.

## Initialization and device selection

Initialize the process-wide context before requesting a backend. The log sink
is called synchronously and must remain alive while the RHI may emit messages.

```cpp
fyuu_rhi::InitializeRHIContext(
    "MyApplication",
    { 0u, 1u, 0u, 0u },
    "MyEngine",
    { 0u, 1u, 0u, 0u },
    &log_sink
);
```

`RequestInstance` returns the process-lifetime instance for the selected backend:

```cpp
auto& instance = fyuu_rhi::RequestInstance(fyuu_rhi::Backend::Vulkan);
auto physical_devices = instance.EnumeratePhysicalDevices();
auto const& physical_device = fyuu_rhi::BestPerformance(physical_devices);
auto device = physical_device.CreateLogicalDevice();
auto scheduler = device.CreateScheduler();

// Create resources and submit command graphs here.
```

`PhysicalDevice::GetInfo()` returns the adapter name and type plus optional
vendor, device, and dedicated-memory information. A missing optional value
means that the backend cannot report it; it does not mean zero.

`Instance::ShareContextOnThisThread()` binds the shared OpenGL context where
OpenGL requires it. Other backends treat the call as a no-op.

## Resources and views

`ResourceFlags` describes memory placement, usage, format, texture shape,
sample count, and allowed view kinds. These flags are a correctness contract:
backends reject contradictory combinations, and every recorded use must have
been declared when the resource was created.

```cpp
fyuu_rhi::ResourceFlags flags;
flags.Set(fyuu_rhi::ResourceFlagBits::DeviceLocal);
flags.Set(fyuu_rhi::ResourceFlagBits::Texture2D);
flags.Set(fyuu_rhi::ResourceFlagBits::TextureView2D);
flags.Set(fyuu_rhi::ResourceFlagBits::TextureViewAspectAll);
flags.Set(fyuu_rhi::ResourceFlagBits::RenderAttachment);
flags.Set(fyuu_rhi::ResourceFlagBits::CopySRC);
flags.Set(fyuu_rhi::ResourceFlagBits::Sample1);
flags.Set(fyuu_rhi::ResourceFlagBits::R8G8B8A8Unorm);

auto texture = device.CreateTexture(width, height, 1u, 1u, flags);
auto view = texture.CreateTextureView(0u, 1u, 0u, 1u, flags);
```

Views are created by their source resource so backend and device ownership can
be checked without exposing native handles. Use `CreateBufferView()` for
buffers. A buffer written by `WriteBuffer`, for example, must include
`CopyDST`; `VertexBuffer` alone does not permit an upload.

## Shaders, pipelines, and resource groups

Pipelines receive Slang program descriptors. FyuuRHI compiles the declared
modules and reflects their resource interface. A graphics pipeline also
describes vertex input, primitive topology, rasterization, multisampling,
depth/stencil state, blending, and attachment formats.

```cpp
auto pipeline = device.CreateGraphicsPipeline(
    {
        .program = {
            .modules = shader_modules,
            .entry_points = entry_points
        },
        .vertex = {
            .buffers = vertex_buffers,
            .attributes = vertex_attributes
        },
        .color_targets = color_targets
    }
);
```

A resource group is created by its pipeline. Its space, slot, array element,
and binding kind must match the reflected interface. FyuuRHI supports both
separate texture/sampler bindings and an explicitly combined binding:

```cpp
std::array bindings{
    fyuu_rhi::pipeline::ResourceBinding{
        .slot = 0u,
        .array_element = 0u,
        .value = fyuu_rhi::pipeline::BindingValue::FromCombined(
            texture_view,
            sampler
        )
    }
};

auto group = pipeline.CreatePipelineResourceGroup(0u, bindings);
```

## Command graphs

A command graph describes binding slots, dependency-ordered nodes, logical
queue requirements, resource accesses, and commands:

```cpp
using namespace fyuu_rhi::execution;

auto builder = scheduler.schedule();
auto target_resource = builder.RegisterResource();
auto target_view = builder.RegisterView();
auto graphics_pipeline = builder.RegisterPipeline();

auto render = builder.CreateNode(QueueType::Graphics);
render
    .Access(
        {
            target_resource,
            AccessMode::Write,
            ResourceUsage::ColorAttachment,
            {}
        }
    )
    .Record(BindPipeline{ graphics_pipeline })
    .Record(
        BeginRendering{
            .area = { 0, 0, width, height },
            .colors = {
                {
                    .resource = target_resource,
                    .view = target_view,
                    .clear = { 0.02f, 0.03f, 0.04f, 1.0f }
                }
            }
        }
    )
    .Record(Viewport{ 0.0f, 0.0f, float(width), float(height) })
    .Record(Scissor{ 0, 0, width, height })
    .Record(Draw{ 3u, 1u, 0u, 0u })
    .Record(EndRendering{});
```

Access declarations are not hints. They must describe the commands accurately;
the backends use them to form batches, transition resources, insert barriers,
synchronize queues, and transfer queue-family ownership. `QueueType` states a
capability requirement, not a promise of a dedicated physical queue.

## Presentation

Presentation is part of the graph and normally depends on the render node:

```cpp
auto present = builder.CreateNode(QueueType::Present, render);
present
    .Access(
        {
            target_resource,
            AccessMode::Read,
            ResourceUsage::PresentationSource,
            {}
        }
    )
    .Record(
        Present{
            .source = target_resource,
            .target = 0u,
            .buffer_count = 3u,
            .vertical_sync = true
        }
    );
```

Bind each native window with `SetPresentationTarget()`. The application still
owns the window and event loop, responds to size changes, and submits frames
until the window closes.

## Starting work and receiving completion

Connect a finished graph to a receiver, fill every registered slot, and start
the operation:

```cpp
auto operation = std::move(builder).connect(Receiver{ state });
operation.BindResource(target_resource, std::move(texture));
operation.BindView(target_view, std::move(view));
operation.BindPipeline(graphics_pipeline, std::move(pipeline));
operation.SetPresentationTarget(native_window);
operation.start();
```

The receiver provides `get_env()` and handles exactly one terminal signal:

- `set_value(CommandGraphResources&&) &&` for success;
- `set_error(std::exception_ptr) &&` for failure;
- `set_stopped() &&` for cancellation.

Before an error or stopped signal, `RecoverBindings(CommandGraphResources&&)`
returns the objects owned by the operation. On success they arrive directly in
`set_value`. Use the matching `TakeResource`, `TakeView`, `TakeSampler`,
`TakePipeline`, or `TakeResourceGroup` operation; each slot can be taken once.

Completion may be delivered from an internal worker thread. The receiver must
synchronize application state shared with that thread. Stop requests are
effective before native submission; already submitted GPU work is not generally
cancellable.

## Validation and diagnostics

Execution proceeds through preparation, parallel command recording, and queue
submission. Binding errors are reported before submission; recording and GPU
errors flow through the receiver's error channel.

Backend diagnostics are written to the configured `fyuu_rhi::log::Sink`.
Automated tests should treat Error and Fatal records as failures even when a
backend or process returns success.

The cross-backend integration test lives at
`lib/fyuu_rhi/test/hello_triangle`. With testing enabled, CTest registers a
bounded run for each configured backend. The executable can also run
interactively:

```text
HelloTriangle <d3d12|vulkan|opengl|webgpu|metal>
```

It covers device creation, upload, pipeline and resource-group creation,
command recording, drawing, presentation, completion, and resize handling.
Metal remains unvalidated until this test passes on Apple hardware with a real
window and event loop.
